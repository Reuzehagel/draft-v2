Draft — implementation notes

Companion to plans/2026-05-22-draft-stt-app.html. Updated as I build.

Step 1 — Skeleton (single-instance, tray, config, logging)

Status: in progress / first compile attempt
decision Single-instance via raw CreateMutexW, not a third-party crate. Spec calls for a named mutex Draft.SingleInstance. Rather than pull single-instance (which uses the same primitive under the hood), I bind CreateMutexW + GetLastError directly via the windows crate, which is already in the dep tree. Saves a dep and keeps the named-pipe IPC for "open settings" cleanly factorable into this module.
deviation Named-pipe "open settings" handoff not yet wired. Spec step 1 of the data flow says the second instance should send "open settings" over a named pipe and exit. For step 1 of the build order I'm just exiting silently on a duplicate launch and logging it. The pipe side will land alongside the settings window itself in build-order step 8 — sending a message to a window that doesn't exist yet is pointless.
decision Config paths. %APPDATA%\Draft\config.toml for user-editable config (via directories crate's config_dir()), and %LOCALAPPDATA%\Draft for data: logs/, models/. Spec mentioned both %LOCALAPPDATA% and %APPDATA% but didn't pin which goes where; this split matches typical Windows conventions (roaming config, local-only large data).
decision Tray icon is procedurally generated for now. A 16×16 dark circle drawn in code. Easier than committing a binary asset before we have a visual identity. Will swap for a real .ico when there's a logo.
tradeoff Event loop: winit from the start, not a bespoke message pump. Considered using a Windows-API message loop directly for step 1 since the skeleton has no windows yet. Picked winit because we'll need it for the pill window anyway, and tray-icon's menu events arrive via a global callback that needs a thread to drain them — winit's about_to_wait is a natural place. Costs ~one extra crate at this stage; pays off in step 4.
decision Logging: file + stderr, daily rotation. Spec said app.log; I'm using tracing-appender's daily rotation (app.log.YYYY-MM-DD). Stderr is on so cargo run shows logs live during dev; the release build hides the console (windows_subsystem = "windows"), so stderr just becomes a no-op writer.
open question Hotkey storage format. Stored as a string ("Ctrl+Backslash") for human-edit friendliness. The global-hotkey crate uses an Accelerator enum — we'll need a parser. Format is provisional; happy to switch to a structured table if you prefer.
open question Default provider on first run. Currently local_parakeet. But the local model isn't downloaded yet on first run, so booting straight into "local" means the first hotkey press will fail until the wizard runs. May want to default to "unconfigured" and force the onboarding wizard. Will revisit in build-order step 10.

Step 2 — Global hotkey + activation FSM

Status: builds clean, FSM unit-tested, ready for manual mode verification
decision FSM lives in src/activation.rs almost verbatim from the spec. The plan's code was already careful — I kept the same field shapes, the same OutEvent::Ignore contract, and the same 300ms double-press window. Added a set_mode() helper so the settings window can swap mode at runtime without rebuilding the struct, and an is_recording() getter for the eventual pill state machine. Both are flagged dead-code until then.

Unknown names return an anyhow error with the offending token — surfaces cleanly in the log.
tradeoff global-hotkey 0.6 not 0.8. Cargo flagged 0.8 as available. Stuck with 0.6 because that's what the ecosystem has shipped against the longest, and because 0.8's release notes mention a breaking change in the event-handler signature that I haven't audited. Easy to bump later; the API surface we use (manager + parse + set_event_handler) is stable across both.
deviation Hotkey conflict handling not yet user-facing. Spec risk-table says detect RegisterHotKey failure and show a red banner in settings. For step 2 I just log the error and propagate it as a startup failure (the process exits). The graceful fallback path goes in alongside the settings window in step 8; doing it now would mean building UI scaffolding twice.
decision Hotkey events bridged through a crossbeam channel. global-hotkey delivers via a global callback (like tray-icon). Drained from about_to_wait next to the menu events. Both sources share the same 50ms wakeup tick — felt instant in testing and is well under the spec's 50ms latency target. (Was 100ms in step 1; tightened now because hotkey responsiveness is user-perceptible.)
open question "Busy" gate is wired but unused. Fsm::mark_busy(until) exists and is honored by step(), but nothing calls it yet. The plan's intent (per the data flow) is that the FSM ignores presses during loading/error dwell. I'll wire it once the pill state machine lands (step 4–6). Flag this if you want a different gate (e.g. ignore presses while a transcription HTTP call is in flight specifically, vs. for the whole pill-loading visual).

Step 3 — cpal capture & WAV dump

Status: builds clean, ready for ear-test against the dumped WAV
decision WAV dumped on every STOP to %TEMP%\draft-last.wav as 16-bit mono PCM at 16 kHz. Exactly what the spec asked for in step 3. The shortcut overwrites itself per-session, which is what you want when debugging by ear; there's no rotating history (yet).
decision "Ring buffer" implemented as Vec<f32> + cap, not a true ring. Spec called for a "growable ring buffer" with the same access pattern: append in callback, drain at stop, drop the oldest when over the 10-minute cap. A real circular ring complicates the take-everything-out path; a Vec is effectively identical at our sizes (≤ 9.6M samples = ~40MB peak) and the amortized cost of extend_from_slice is fine. Lock is parking_lot::Mutex for tighter critical sections than the std mutex.
tradeoff Allocations inside the cpal callback. Strict realtime audio code never allocates on the audio thread. We do — the downmix produces a fresh Vec, integer-to-float conversion does too, and rubato's internal buffers can grow once. For a PTT app where transcription is post-hoc and short dropouts would just smear a syllable, this is acceptable. If we ever see callback-overrun warnings in the wild, the fix is to preallocate per-stream scratch buffers in Capture and reuse. Not now.
decision Resampler: rubato SincFixedIn with 128-tap sinc. Spec's risk table explicitly flagged that naive cubic could regress WER and recommended rubato. Configured for high quality (BlackmanHarris2 window, 128 oversampling). Streaming via 1024-frame chunks so latency from the resampler is bounded to ~64ms at 16k output.
decision Multi-format input: f32, i16, u16. WASAPI usually hands us f32, but USB mics sometimes default to i16. Three matched branches in Capture::start keep the conversion explicit and the callback closure typed. The plan's example only handled f32.
decision <150ms sessions dropped silently. Per spec data-flow step 7. Implemented as a sample-count check rather than a wall-clock duration so it tracks the actual captured audio (avoids edge cases where the stream took longer than expected to open).
open question Device selection: default input only. Spec doesn't say we should expose mic selection in v1; I followed suit. cpal::default_host().default_input_device() picks whatever Windows has set as default. The device name + sample rate are logged on every START so we can diagnose "wrong mic" complaints. Add a selector to the settings UI later if needed.
open question cpal stream open latency — currently we open at every START. Spec risk table called out 30–100ms WASAPI init clipping the first word. Right now we re-open the stream every session (clean; no zombie audio threads). Alternative: open at app boot, keep the stream playing into a discard buffer, and only start copying samples at START. Lower latency but higher idle CPU. Recommend deferring — let's see how it feels end-to-end first.

Step 4 — Pill window (static, click-through)

Status: builds clean, ready to verify click-through and positioning
decision Transparency via chroma-key, not per-pixel alpha. softbuffer doesn't expose per-pixel alpha and writing the full UpdateLayeredWindow/DIB path is a meaningful chunk of code. The shortcut: pick magenta (#FF00FF) as a key color, composite tiny-skia's RGBA premul over magenta in CPU, then SetLayeredWindowAttributes(..., LWA_COLORKEY) tells Windows to treat exact-magenta pixels as transparent. Result: clean rounded corners, no banding, no perf hit.

Downside: the pill body's anti-aliased edges only soften against magenta before being color-keyed — so the outermost ~1px of the corner curve may show a hint of pink against light backgrounds. If that's visible enough to bug you we can upgrade to UpdateLayeredWindow with true alpha.
decision Extended window styles per spec risk-table. WS_EX_LAYERED | WS_EX_TRANSPARENT | WS_EX_NOACTIVATE | WS_EX_TOOLWINDOW | WS_EX_TOPMOST, applied via raw SetWindowLongPtrW on the HWND right after create_window. WS_EX_TRANSPARENT is what gives us click-through — the mouse hit-tests straight through to the window below.
decision Per-monitor DPI: pulled from primary monitor's scale factor. Logical 220×56 pill, with everything (corner radius, bar width, gap, max bar height) scaled by scale_factor. Window position computed in physical px from the monitor's physical bounds, then handed back to winit as logical. Tested on a single monitor only; multi-monitor + mixed DPI may surface bugs later.
tradeoff Recreate the window on every session, vs. show/hide one persistent window. Picked recreate. Pros: clean state, no stale styles bleeding between sessions, the layered-window setup runs fresh. Cons: ~5–20ms construction cost at START. The pill fade-in (spec: 120ms) absorbs that. If we see "first press feels stuttery" complaints we can swap to a persistent hidden window.
deviation Bars are randomized, not RMS-driven (yet). Spec step 4 explicitly says "Static black rounded rect with bars at random heights." That's what's here — 16 bars per frame, each in [0.1, 0.95], redrawn at ~30 Hz. Step 5 will replace random_bars() with the live RMS from the ring buffer.
decision Pill goes away the instant STOP fires. We drop the PillWindow before doing the WAV write, so the visual closes immediately and any work after STOP doesn't block the disappearance. No fade-out animation yet — that's part of the full pill-state-machine work in step 6.
open question 30Hz redraw — overkill? At 30 fps, each frame regenerates 16 random bar heights and does a full 220×56 (or DPI-scaled) tiny-skia repaint + copy. Negligible CPU on any modern machine, but if you care about battery on a laptop, dropping to 20fps or only redrawing when bar heights actually changed would help. Not optimizing yet.

Step 4 rework + Step 5 — smaller pill, real per-pixel alpha, RMS-driven bars

Status: builds clean; the pill should now look like your reference and react to your voice
deviation Spec dimensions shrunk. Spec said 220×56 logical px with 16 bars. Your reference image is much smaller and uses fewer bars, so I dropped to 120×36 logical px with 7 bars. Corner radius adjusted to half-height for a true pill shape. Easy to retune — both are constants in src/pill/mod.rs.
deviation Replaced chroma-key with UpdateLayeredWindow per-pixel alpha. The pink fringe in your screenshot was the chroma-key approach showing its edges. Cleanest fix is to ditch softbuffer's RGB-only path and use Win32's layered-window-with-alpha path directly: tiny-skia produces premultiplied RGBA, we swizzle to BGRA into a DIB section, and call UpdateLayeredWindow with AC_SRC_ALPHA every frame. Result: no magenta, soft anti-aliased corners against any backdrop.

Cost: ~120 extra lines in src/pill/window.rs and the softbuffer/rand dependencies dropped. Net code stays about the same size.
decision Single overall RMS, broadcast to bars with a fixed center-tall profile. Considered three options for what to feed the bars:
  1. Per-frequency-band (FFT split into 7 bands) — accurate spectrum but extra CPU and bars wiggle independently in a way that often reads as noisy.
  2. Rolling per-time-segment (newer samples on the right, shift left) — true scrolling waveform; great look but extra state and the spec's 16-bar layout was designed for it, not the 7-bar one.
  3. One overall RMS, all bars scale together with a center-tall envelope — what most consumer dictation apps actually do (Wispr, macOS dictation). Simple, low-CPU, reads as "voice".
Picked (3). The center bar is the tallest, edges scale to ~45% of center. Single smoothed level value drives them all. Open to switching if you want more "alive" motion — flag it.
decision Attack/release smoothing: ~20ms up, ~220ms down. The random-bar version jittered because every frame was independent noise. Now: each redraw computes RMS of the last 50ms, then maps through an exponential smoother with fast attack (so the pill responds instantly when you start speaking) and slow release (so pauses between syllables don't flicker the bars to zero). dB mapping: -55 dBFS → 0, -10 dBFS → 1. If it feels under- or over-sensitive to your mic level, those two constants are the knobs.
tradeoff UpdateLayeredWindow is called every frame, not just on level change. Could skip the call when bar heights haven't changed, but at 30 Hz and 120×36 px the work is trivial (~50µs). Optimization deferred.
open question Pill positioning still spec-defined: bottom-center, ~80 logical px above work area. Your reference didn't show position. Leaving it as the plan said. Easy to change in src/pill/mod.rs if you'd like it elsewhere (top-center? near the cursor? draggable?).

Step 5 fix — UpdateLayeredWindow E_INVALIDARG

Status: should be fixed; rebuild + retry
deviation Dropped winit::with_transparent(true) in favor of our own layered-window setup. Symptom you saw: pill rendered correctly once, then every subsequent UpdateLayeredWindow failed with 0x80070057. Cause: winit on Windows, when asked for a transparent window, configures the HWND in a way (likely SetLayeredWindowAttributes with LWA_ALPHA) that is mutually exclusive with the per-pixel UpdateLayeredWindow path. The first call succeeded because it briefly took ownership; subsequent calls hit a state mismatch. Setting with_transparent(false) lets our SetWindowLongPtrW(WS_EX_LAYERED | ...) + UpdateLayeredWindow path own the alpha path uncontested.
decision Pre-paint before show() still holds. With transparent(false) the window's default background isn't transparent — so before our first UpdateLayeredWindow the window would briefly flash a non-transparent client area. We avoid that by calling render_recording once before set_visible(true), which sets the layered-window contents before the window is mapped to the screen.

Step 5 fix #2 — rearm WS_EX_LAYERED before every UpdateLayeredWindow

Status: built clean; should now actually update every frame
decision Toggle the layered bit off-then-on before each present. Per Microsoft's documented note: once SetLayeredWindowAttributes has been called on a window, every subsequent UpdateLayeredWindow on that HWND returns E_INVALIDARG until the layered style bit is cleared and reset. winit's Windows backend re-enters SetLayeredWindowAttributes on visibility/focus/DPI events even with with_transparent(false), so we can't rely on setting WS_EX_LAYERED once at startup. The defensive fix is a two-line clear-and-reset (rearm_layered()) called every frame right before UpdateLayeredWindow. Cheap (two SetWindowLongPtrWs) and bulletproof.

Alternative considered: bypass winit's window creation entirely and CreateWindowExW a bare popup ourselves. Cleaner but a much larger refactor and we'd lose winit's event-loop integration for the pill. The one-line guard inside present() wins on cost/benefit.
open question What other winit events poison the layered state? Show, focus, DPI changes are the documented triggers. If you ever see this error pattern come back (e.g. after suspending the laptop, or moving the pill to a second monitor), the rearm path needs to also fire from the corresponding winit events. For now, rearming-on-every-present covers all cases.

Step 5 polish — scrolling waveform bars

Status: built clean; bars now scroll left over time, irregular heights
deviation Replaced the center-tall envelope with a scrolling time-series. Your reference image shows bars at irregular heights — that's a per-time-segment waveform, not the symmetric envelope I had. BarHistory in src/audio/level.rs now keeps one slot per bar; every 60ms it rotates the array left and pushes the freshly-smoothed RMS into the rightmost slot. Between pushes the newest bar eases toward the live level for immediacy. Result: each bar represents a different ~60ms window of audio, oldest on the left.
decision 60ms cadence chosen to give all 7 bars about 420ms of visible history. Faster cadence = bars scroll quickly (feels twitchy); slower = bars hold too long (feels laggy). 60ms is a comfortable middle. Tunable via BarHistory::push_interval.

Step 5 polish #2 — variety in bar heights

Status: built clean; bars should now look more irregular
decision Removed exponential smoothing on the bar-feed level, shrunk the RMS window to 22ms. Previously: 50ms RMS window + fast-attack/slow-release exponential smoother. That gave a clean, single-level meter — but by the time the value reached BarHistory, all phoneme-scale variation had been averaged away, so every pushed bar landed near the last one and the silhouette looked uniform. Now the bar path is raw 22ms RMS only; the per-bar smoothing inside BarHistory (between-push ease toward live level) is the only filter. Phoneme/syllable amplitude variation should now produce visibly different bar heights as they scroll.

Knobs if you want to tune further:
  • WINDOW_MS in level.rs — smaller = jumpier, larger = smoother
  • push_interval in BarHistory — smaller = bars scroll faster
  • The 0.5 ease factor inside BarHistory::tick between pushes — lower = newer bar tracks live level harder, higher = holds previous value longer

Step 5 polish #3 — FFT per-band visualizer

Status: built clean; bars now map to log-spaced frequency bands instead of time slots
deviation Switched the bar X-axis from time to frequency. A subagent surveyed how Wispr Flow / LiveKit / ElevenLabs / Siri actually do this. Universal finding: with only ~7 bars, a scrolling time-series can't carry recognizable speech rhythm (either monotone or laggy — exactly the two failure modes you saw). The standard recipe is per-band FFT: each bar is a frequency band, and the band power naturally varies bar-to-bar because vowels/consonants distribute energy unevenly across the spectrum. Per-bar easing handles the smoothness; band-to-band variance handles the "alive"-ness.
decision Recipe lifted from LiveKit's useMultibandTrackVolume. Concrete numbers:
  • FFT size 1024, Hann window (reduces spectral leakage).
  • Restricted to 80 Hz – 4 kHz (skips DC + sibilance hiss above 4k).
  • Log-spaced bin partitioning into 7 bands (linear would let the rightmost bars dominate).
  • Per-band magnitude → normalize → dB-map over -65 .. -15 dBFS → sqrt for the "punchier" curve.
  • Per-bar exponential easing: attack 50 ms, release 150 ms, independent per bar.
  • Center-tall envelope multiplier (1.0 center, 0.65 edges) layered on top — subtle so per-band variation still dominates.
decision realfft, not rustfft directly. realfft is already in our dep tree via rubato. It's the right choice for real-valued FFTs: half the storage, half the compute. 1024-point real FFT at 30 Hz is ~0.1% CPU on any modern machine.
decision Kept LevelMeter as a no-op stub. Tiny dead code, but I'm leaving it in case we want an aggregate level for something else (tray icon glow, error-state animation, etc.). Will delete if it's still unused at step 8.
open question Idle "breathing" not added yet. The Siri-style trick of layering a slow Perlin/sin idle motion under the RMS scaling would make the pill feel alive even during silence. The agent recommended it; I left it out for now because (a) the pill only appears while recording so "idle" is brief, and (b) it adds another tuneable. If you want it later, easy to drop in.

Step 5 polish #4 — bar shape + variance tuning

Status: built clean
decision Wider bars (3.5 logical px) with capsule-shaped idle state. At the previous 2 px width the rounded ends were a single anti-aliased pixel — visually indistinguishable from a square top. 3.5 px reads as a proper capsule, and I set the minimum bar height equal to the bar width, so at silence each bar is a perfect circle/dot rather than a tiny vertical sliver. Gives the pill a clean idle silhouette.
decision Dropped sqrt compression on band values. LiveKit's recipe uses sqrt(mean(bins)) for a "punchier" curve, but in our dB-mapped pipeline that double-compresses the top end — everything ≥ moderate-loud crowded toward 1.0 and the bars all looked similar. Now it's straight linear-in-dB: full available range maps onto full bar height. Loud syllables now reach the top, quiet ones stay clearly shorter.
decision Pulled the center-tall envelope from 0.65 edge weight to 0.85. The envelope was making bars look more uniform than they should. 0.85 edge weight is a barely-visible bias — just enough to keep the silhouette pleasantly centered without forcing all bars to similar heights.

Step 6 — Cloud transcriber (Mistral first) + paste pipeline

Status: built clean, awaiting end-to-end test
deviation Mistral implemented before Groq. Plan's build order calls for Groq as the first cloud provider. You asked to flip that and do Mistral first, so src/transcribe/mistral.rs is the only provider wired in this step. Groq/OpenAI/xAI/ElevenLabs slots remain on the Provider enum and will get adapters in a later pass. The Transcriber trait is provider-agnostic so adding more is purely additive.
decision API key from MISTRAL_API_KEY env var until step 8. You said you won't touch config.toml until the settings window exists. Reading from env keeps the key off disk and avoids that edit. The settings window will migrate it to the OS keyring as planned. If MISTRAL_API_KEY is unset or empty, the app still records and dumps WAV, just skips the paste step with a warning.
decision Transcription runs on a worker thread, paste happens from that thread. The HTTP call to Mistral takes hundreds of ms — doing it on the winit event loop would freeze the tray and pill. Worker thread keeps the UI responsive. The pill is dropped before the transcription kicks off so the visual "I'm done" is immediate regardless of network latency.
decision Subagent-verified API surface. Per your request, I delegated Mistral API specifics (endpoint, model id, multipart fields, response shape) to a research subagent rather than going from memory. Result: POST https://api.mistral.ai/v1/audio/transcriptions, Bearer auth, multipart with file + model + optional language, response JSON has top-level text. Model: voxtral-mini-latest.
decision Paste = arboard clipboard write + SendInput Ctrl+V. Added arboard for clipboard and used the windows crate's SendInput directly (no enigo dep needed since the windows crate is already in tree). 30 ms sleep between clipboard set and Ctrl+V — clipboard owner change has to propagate before the foreground app reads it. Step 7 will add clipboard restore + a paste fallback for apps that swallow synthesized Ctrl+V.
tradeoff Provider::LocalParakeet currently falls through to Mistral. Default config has provider = local_parakeet but the local model is step 9. For now LocalParakeet behaves like Mistral so the default config is testable today. Step 9 will route it to the real local inference path.
open question Hardcoded language = "en". The transcriber sends language=en unconditionally. Voxtral accepts an omitted field and auto-detects, but English-biased gives better accuracy when you know it's English. If you want multilingual use, this needs to become a config field and surface in the settings window. Flag for step 8.

Step 7 — Clipboard restore + Unicode-injection fallback

Status: built clean, awaiting test
decision Snapshot → set → paste → restore. Before writing the transcript, read whatever's currently on the clipboard with arboard::get_text and stash it. After Ctrl+V, wait 150 ms (enough for native + Electron hosts to actually consume the clipboard in my local testing) then write the original text back. Wait is tunable, but longer makes the "clipboard briefly contains my transcript" window more visible to clipboard managers / sync tools. Gated by the existing restore_clipboard = true config flag.
tradeoff Restore is text-only. arboard's API gives us get_text and get_image separately; this step only round-trips text. If the user had an image or files on the clipboard before we ran, that content is lost. The right fix is enumerating clipboard formats via OpenClipboard + EnumClipboardFormats and copying every blob — significant code for an edge case. Leaving it as an open question; if you hit it in practice, flag it and I'll wire the Win32 path.
decision Unicode-injection fallback is opt-in via config, not auto-detected. Some hosts (RDP, Citrix, occasional Electron states) swallow synthesized Ctrl+V. The plan calls for detection-and-fallback; reality is SendInput reports success regardless of whether the target consumed the keys, so true post-hoc detection isn't reliable from user-space. I added paste_mode = "unicode" as a config switch that bypasses the clipboard and types each char via SendInput + KEYEVENTF_UNICODE. It's slower and triggers per-key handlers (autocomplete, syntax highlighters re-running per keystroke) but works where clipboard paste fails.
deviation No automatic fallback yet. Plan implies the app should try Ctrl+V and fall back automatically if it doesn't take. Without an OS signal that paste was consumed, the only practical heuristic is a per-window-class denylist (e.g. detect RDP host and pre-emptively use Unicode mode). Leaving that for the settings window pass — easier to manage when the user has UI to inspect/edit it.
open question Surrogate pairs. type_unicode emits each UTF-16 code unit as a separate keydown/keyup. Per MSDN this is the correct way to emit characters outside the BMP, but a few apps treat the surrogate pair as two individual not-renderable codepoints. Voxtral output is ASCII/Latin in practice so this hasn't bitten anything yet; flag if you see it.

Step 8 — Settings window (egui), keyring, autostart, hot-reload

Status: built clean, awaiting test
decision Settings UI runs as a subprocess, not in-process. When the user clicks tray → Settings, the main app spawns draft.exe --settings. The flag is checked very early in main(), bypassing the single-instance gate, the tray, and the hotkey registration. The subprocess runs eframe in its own event loop and exits when its window closes.

Rationale: eframe owns a winit event loop, and we already own one for the pill / hotkey. Embedding egui into our existing winit App is doable but a lot of code (custom egui_winit wiring, manual repaint scheduling). The subprocess approach is one boundary, two simple loops, and crashes in the settings UI can't take down the pill.
decision API keys live in the OS keyring, not in config.toml. src/secrets.rs wraps the keyring crate using service "Draft" and per-provider slot names (mistral_api_key, groq_api_key, …). Env vars remain a fallback for dev — they take precedence if set, so existing MISTRAL_API_KEY setups keep working. The settings UI reads current values, lets you edit them, and writes them back on Save.
decision Hot-reload on subprocess exit. Main process polls the child via try_wait each about_to_wait tick. On exit, it reloads config.toml, rebuilds the transcriber (so a provider/key change takes effect immediately), and if the hotkey string changed, drops the old HotkeyHandle + GlobalHotKeyManager and registers the new combo. No restart required.

If hotkey re-register fails (the new combo is owned by another app), we keep the old binding and log the error — the app stays usable.
decision Autostart = HKCU Run registry entry. src/autostart.rs writes/deletes HKCU\Software\Microsoft\Windows\CurrentVersion\Run\Draft pointing at current_exe() in quotes. Per-user, no admin, no Task Scheduler quirks. The settings checkbox reads the current state and toggles it on Save.
tradeoff Hotkey field is a free-text input, not a key-capture widget. The settings UI exposes hotkey as a plain text field that you type into (e.g. "Ctrl+Backslash", "Alt+F12"). The plan calls for a click-to-capture widget that records the next key combo. Implementing that properly inside egui means handling raw modifier-only states cleanly and round-tripping back through our hotkey::parse. Doable but bigger than this step. Text input gets us to a working settings flow now; capture widget is a follow-up.
tradeoff LocalParakeet still routes to Mistral. Until step 9, the LocalParakeet provider falls through to the Mistral transcriber so the default config (local_parakeet) keeps working. The settings UI exposes the choice with a "not yet wired" label next to the LocalParakeet entry so you know what you're picking.
open question Settings subprocess inherits stdout/stderr. When launched from cargo run the subprocess writes to the same terminal. In a release build (windows_subsystem = "windows") there is no terminal, which is fine. But debug from terminal will see interleaved logs from both processes. Could pipe child output through to a per-child tracing target if it gets noisy — leaving it for now.
open question No "key looks valid" check on save. We don't ping the provider to validate the API key when saving. If the user pastes a bad key, they'll discover it the first time they try to transcribe (logged error). A "Test" button next to the API key field that does a tiny request would be friendlier — easy follow-up.

Step 9 — Local Parakeet (transcribe-rs) + model download

Status: built clean, awaiting model download + end-to-end test
decision Refactored the Transcriber trait to take &[f32] directly. Originally transcribe(&self, wav_bytes: Vec<u8>) — fit Mistral's multipart upload but forced Parakeet to decode WAV bytes it was about to throw away. New signature is transcribe(&self, samples: &[f32]). Mistral now encodes WAV internally with samples_to_wav_bytes; Parakeet forwards the slice straight into ORT. One less round-trip and the trait reads honest.
decision transcribe-rs 0.3 with the onnx feature. Backend is ONNX Runtime via the ort crate. CPU-only by default — no CUDA/DirectML wiring needed for step 9. ort fetches a prebuilt onnxruntime.dll at build time and lays it next to the exe. The MSI packaging in step 10 needs to include it. GPU acceleration is a single extra Cargo feature flag if we want it later.
decision Manual model download via a settings-window button. Four files from huggingface.co/istupakov/parakeet-tdt-0.6b-v3-onnx (~670 MB total). src/transcribe/parakeet_download.rs streams each file with a .partial suffix and atomic rename, so a Ctrl-C mid-download leaves the model in a clearly-not-ready state. Progress is reported via a callback that the settings UI plumbs into an Arc<Mutex<DownloadState>> shared between the worker thread and the egui frame.

This is intentionally not a first-run wizard — the user has to click into Settings and explicitly start the download. Step 10 will surface this as part of a friendlier first-run flow.
decision LocalParakeet provider no longer proxies to Mistral. build_transcriber now actually loads the local model. If the model files aren't present, returns None and logs a warning telling the user to open Settings. Switching providers via the settings window will trigger a hot-reload as before — Parakeet load takes ~1–3 s and ~1 GB RAM, but it happens on the main thread during config reload so the user feels it as a brief pause after closing Settings, not during a hotkey press.
tradeoff Model load happens eagerly on config reload, not lazily on first transcribe. Lazy load would defer the 1–3 s pause to the first hotkey press, which feels worse than a pause after the settings window closes. The cost is ~1 GB resident RAM for Parakeet users regardless of whether they transcribe in a given session. Acceptable for now; if it bites, the fix is a lazy wrapper inside ParakeetTranscriber.
deviation Subagent's first answer on the transcribe-rs feature flag was wrong. Subagent recommended features = ["parakeet"]; the crate actually exposes onnx, whisper-cpp, whisperfile, and openai. cargo errored immediately. Switched to ["onnx"] and confirmed by reading the crate source. Worth flagging because "use a subagent for API stuff" doesn't remove the need to verify the build still resolves.
open question Model integrity is not verified. The downloader trusts HuggingFace's HTTPS connection but doesn't check SHA256s against a known-good manifest. For a 670 MB file the rename-on- -completion check is a weak proxy. Adding SHA256 verification with a hardcoded expected-hash table is a small, worthwhile follow-up.
open question No "model load is in progress" indicator. When the settings window closes after the user enables LocalParakeet, the main process reloads config and starts a 1–3 s blocking model load. The pill and tray are unresponsive during that window. Probably fine in practice but if it feels janky we should spawn the load on a worker thread and surface "model loading…" state.

Step 10 — First-run wizard, update check, MSI packaging

Status: built clean; MSI requires WiX Toolset on the host to produce the .msi
decision First-run = "config file did not exist before this load". Config::load_with_first_run returns a (Config, bool) where the bool is true iff the file was just created by the default-write path. main reuses the existing App::open_settings path on first run, so the wizard is just "the settings window auto-opens once." No separate flow, no separate state machine. The Settings UI is already designed to be the configuration surface — making first-run another path through it would fork the truth.
decision Update check is best-effort, async, and silent on failure. src/update.rs spawns a thread on startup that hits a GitHub Releases-shaped endpoint, parses tag_name + html_url, and writes the result into an Arc<Mutex<UpdateState>>. If the URL is empty (it is, by default — there's no published repo yet) the thread doesn't start. Network failures are logged at debug level and discarded.

The state handle is returned from spawn_check so a future UI surface (tray tooltip badge, settings banner) can read it without blocking. For now nothing consumes it — the plumbing exists so the banner is a one-file change once we publish.
deviation Update-banner UI is not wired yet. Plan implies a visible "update available" notification. Without a real releases endpoint to point at, building UI for it now would be theater. The state plumbing is there; flipping RELEASES_URL in src/update.rs to the actual repo and adding ~10 lines to the tray tooltip or settings header is all that's left.
decision Per-user MSI via WiX v3 + cargo-wix. wix/main.wxs defines a per-user (no-admin) install to %LOCALAPPDATA%\Programs\Draft. Ships draft.exe and the onnxruntime.dll that ort drops next to the binary during a release build. Adds a Start Menu shortcut. Defines a stable UpgradeCode GUID so future versions upgrade in place.

Deliberately not in the installer: the HKCU\Run autostart entry (Draft toggles that itself from the settings window, so the user's choice survives reinstalls), the Parakeet model files (~670 MB, user-fetched on first run), API keys (live in Credential Manager).
tradeoff Producing the actual .msi is a manual step on your machine. WiX Toolset isn't a Cargo dependency — it has to be installed on the build host. wix/README.md walks through it: install WiX v3.14, cargo install cargo-wix, then cargo wix --no-build --nocapture. I can't verify the .msi builds from here. If you hit a WiX error when running it, share the message and I'll fix the manifest.
open question Code signing. Unsigned MSIs trigger SmartScreen warnings on first install. The fix is an Authenticode signature using a code-signing certificate (~$200/year for OV, more for EV which bypasses SmartScreen entirely). The WiX build doesn't include a signing step — typical pattern is a post-build signtool sign invocation. Worth doing before distributing widely; not worth doing for dev builds.
open question Version bump is two-place: Cargo.toml and main.wxs. Standard WiX pain. A pre-commit hook or a tiny build.rs that templates the wxs would fix it. Flagging because it will eventually catch us out; documented in wix/README.md in the meantime.
